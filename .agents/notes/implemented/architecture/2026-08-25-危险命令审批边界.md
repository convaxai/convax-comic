# 危险命令审批边界

## 背景

上游 `workspace-write + ask` 的 `ask` 只在显式扩大 sandbox 时触发；它不
分析工作区内命令本身。PLAN 的保守姿势还要求直接可见的危险命令进入审批，
但把字符串匹配描述成完整 shell 安全解析会制造虚假边界。

## 决策

- 所有产品 profile 挂载 Host-only `@convax/command-guard`，经标准
  `tools/pre-execute` 返回 `ask`，复用上游 ApprovalService、审计事件和 UI。
- 只匹配高置信、直接可见的 `bash`/`pwsh` 破坏族：递归/强制删除，
  `git reset --hard` / `git clean -f`，文件系统格式化、`dd of=`、磁盘擦除，
  递归 chmod/chown，强杀进程，以及常见 PowerShell 对应形式。
- 分析器识别引号外的 `;`、`&`、`&&`、`||`、pipeline，并有限递归一层常见
  `shell -c`。普通调用严格委托 `next()`，不改写参数、不自行执行。
- 文件 sandbox 仍是强制边界；command guard 是额外的人类决策点，不是
  恶意代码隔离器。

## 被否方案

- **所有 shell 命令都审批**：安全但让正常 agent 工作流退化为逐命令确认，
  与 workspace-write 的产品默认相矛盾。
- **简单子串匹配**：会把 `echo "rm -rf /"` 等数据误判为命令。
- **实现完整 shell parser / 静态程序分析**：shell 的动态展开、alias、脚本
  和通用解释器使其无法在 M1 形成可信完备边界。
- **自建审批 UI/broker**：重复上游已有 Cordis 服务和审计通道。

## 可证伪的验收证据

- 规则单测覆盖 POSIX、PowerShell、多段命令、nested shell 与 quoted-data
  反例。
- 危险调用返回 `ask`；普通/非 shell 工具精确调用 `next()`。
- tools provider 卸载时 guard fiber 回到 PENDING、事件 effect 清空；恢复后
  重新 ACTIVE。
- profile dump 显示每个 profile 都挂 `app-command-guard`。

## 遗留风险

命令替换、动态字符串、alias/function、`eval`、脚本文件及 Python/Node 等
通用解释器可隐藏破坏操作。后续若需要部署级 allow/deny policy，应基于
结构化执行 provenance 或 OS 级强制机制扩展，不能只堆正则。
