# rc.2 npm 运行闭包

## 背景

DeepSeek Harness 的 npm bundle 用 peer dependency 表达同一 Cordis 树上的
服务关系。Yarn 不会把 bundle 的 peer 自动变成 Electron Builder 可遍历的
物理依赖；只依赖顶层 `@deepseek-ai/dsh` 会得到能解析 CLI、却不一定能装载
完整 profile 的发布物。同时，源码 submodule 只能用于审计，不能偷偷补足
生产依赖。

## 决策

- 审计基线固定 submodule commit，产品运行固定 npm
  `0.1.1-rc.2`；两者由 `upstream.json` 和布局门禁绑定。
- `@convax/desktop` 显式声明参考 profile 所需的 Cordis、DSH Host/Client、
  React 与 native 运行依赖，全部使用精确 rc.2 版本。lockfile 中 190 个
  `@deepseek-ai/dsh*` resolution 必须全部落在同一版本。
- 产品插件继续把 Cordis 声明为 peer，由 profile 的同一个宿主提供，避免
  多份 Cordis Context 类型和运行实例。
- 开发与打包启动都先物化纯数据 profile，再把产品包挂到该 profile 的
  Node resolution fallback。打包态每个真实来源必须位于应用
  `Resources`，禁止回指 worktree 或 submodule。
- 不使用 `packageExtensions` 伪造上游 bundle 内部服务 provider；Yarn 的
  YN0086 会保留为可见的上游发布元数据告警，真实 Loader 与产物 smoke 才是
  闭包是否完整的判据。

## 被否方案

- **只列顶层 DSH bundle**：Electron Builder 无法从 Cordis 配置推导运行时
  peer，打包闭包不完整。
- **从 submodule 执行构建产物**：发布物依赖源码 checkout，pin 审计面和
  生产运行面混在一起。
- **用范围版本补 peer**：一次安装可混入不同 rc，dump 与 ABI 不可复现。
- **批量 packageExtensions 消警**：把 Cordis 服务关系伪装成包管理器依赖，
  既掩盖上游元数据问题，也不能证明 Loader 组合真的可运行。

## 可证伪的验收证据

- `yarn check:layout` 校验 gitlink/checkout/manifest、空 patch 清单、精确
  Electron/Node pin，以及 190 个同版 DSH lock resolution。
- `yarn smoke:upstream` 用 npm 闭包真实启动两个 profile，Loader 均完成。
- `yarn package:dir` 检查产物依赖不是 symlink、realpath 不逃逸
  `Resources`，并用产物内 Node/DSH 在空 PATH 下完成鉴权 Web 启动。
- `yarn install --immutable` 成功；失败 peer 解释均来自上游 rc.2 bundle
  内部声明，产品 workspace 没有失败 peer。

## 遗留风险

上游尚未发布机器可读的 profile 生产闭包，当前清单需随 pin 升级重新审计。
未来若上游修正 bundle 元数据，应优先收缩显式依赖并删除相应告警，不把本
清单永久当作上游 API。
