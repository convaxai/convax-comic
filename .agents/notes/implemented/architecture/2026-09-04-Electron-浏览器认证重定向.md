# Electron 浏览器认证交换跟随一次性重定向

## 背景

DSH BrowserAuth 用带一次性 token 的同源根 URL 签发 HttpOnly cookie，再以 303 重定向到干净 `/`。桌面壳原先用 `session.fetch(..., { redirect: 'manual' })` 读取 303；当前 Electron `net.fetch` 会把这种手动重定向作为 `Redirect was cancelled` 异常，导致运行时已经就绪但 BrowserWindow 永远落入通用加载失败页。

## 决策

- BrowserAuth 交换改用 Electron `net.request` 的 `redirect: 'manual'`；继续显式携带仅存于当次启动内存的控制面 header，并开启同一 Electron session 的 cookie credentials。
- `redirect` 事件中只接受一次 HTTP 303 + GET 且目标严格等于当次随机 loopback origin 的干净根 `/`，同步调用 `followRedirect()`；任何跨 origin、非根路径、query、fragment、二次重定向或最终非 200 响应均失败。
- 响应仅用于完成 cookie 交换并立即 drain，再由 BrowserWindow 加载干净 origin。一次性 BrowserAuth token 不进入最终导航、日志或存储。

## 被否方案

1. **使用 `session.fetch` 手动读取 303**：Electron `net.fetch` 当前实现会取消该请求，已被实机复现，否决。
2. **使用 `session.fetch` 自动跟随**：当前 Electron 的 Response 不提供最终 URL，无法证明跳转仍在精确 authority；也不应冒险把控制 header 跟随到未验证目标，否决。
3. **把一次性 token 直接交给 BrowserWindow 导航**：token 会进入页面 URL 与导航历史，扩大暴露面，否决。
4. **绕过 BrowserAuth，仅依赖控制 header**：破坏 DSH Host Connection 的既有浏览器会话认证，否决。

## 验收证据

- Main-process 诊断捕获原实现的精确错误 `Redirect was cancelled`。
- Desktop 单测覆盖 manual 参数、控制 header、session credentials、同步 follow、精确 redirect 目标和最终状态校验。
- preload、导航白名单、host/port、profile 与 token 生命周期均未变化。

## 遗留风险

若未来 Electron 改变网络行为，应重验 `net.request` 的同步 redirect 事件与 session cookie 交换，不依赖 `net.fetch` 的空 Response.url。
