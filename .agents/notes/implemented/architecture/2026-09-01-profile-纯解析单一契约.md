# Profile 纯解析单一契约

## 背景

桌面生产物化与仓库脚本分别实现了产品 patch 的纯数据解析、`__jsExpr`/`!!js` 拒绝和 `insert[].name` 校验。安全规则重复会产生 gate 与生产路径漂移，但两侧的 package resolver、同步/异步链接、启动 argv 和打包 artifact 检查属于不同执行环境，并非同一职责。

## 决策

- 只抽取无 IO、无环境状态的 patch 解析与 package name 收集契约，由 desktop 生产物化和 scripts 门禁共同调用。
- desktop 构建必须把共享源码内联到 `lib`，运行与打包产物不得依赖仓库 `app/scripts` 路径。
- `check-profiles` 保留对 `process.env`、`ctx.` 等产品配置禁用形态的额外 raw oracle；package-dir 与 packaged-smoke 保留独立 artifact 解析，避免生产实现与最终产物检查同源失效。
- resolver、sync/async symlink、`buildDshArgs`/`profileLaunchArgs` 继续按各自执行边界实现，不为减少相似行数制造跨层适配器。

## 被否方案

- **把 resolver、链接与 argv 全塞进所谓纯模块**：这些函数依赖 fs、resolve base、同步模型与运行环境，不是纯契约。
- **让所有 smoke 复用生产 parser**：会降低独立验证价值，使同一缺陷同时出现在实现和 oracle。
- **让 desktop 运行时直接加载仓库脚本文件**：打包后路径不存在，也违反 Resources 闭包边界。

## 可证伪的验收证据

- desktop 生产物化与 script runtime 对 `!!js`、`__jsExpr`、根数组和 package name 使用同一个共享定义并有直接单测；独立 gate oracle 继续覆盖同一安全结论。
- desktop build/typecheck/test、profile gate、dump-config gate、真实 upstream smoke 与 packaged smoke 全绿。
- 构建后的 desktop Host 产物不存在指向仓库共享源码的运行时 import/require。

## 遗留风险

独立 artifact oracle 仍会保留少量 package name 正则和 YAML 解析重复，这是为检查最终复制资源而刻意保留。未来只有在上游提供机器可读 profile schema 后，才应继续收缩这层独立性。
