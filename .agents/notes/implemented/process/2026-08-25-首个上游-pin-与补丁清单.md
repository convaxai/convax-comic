# 首个上游 pin 与补丁清单

## 背景

M1 需要同时确定审计用源码 pin 和产品运行时版本。参考桌面仓库
`2172b1b2f2b0de4c2b3a1d8b55f11f8083a9305e` 固定的 Harness gitlink 与
上游当前 `dsh-v0.1.1-rc.2` 一致；上游仍明确处于 developer preview，
兼容性变化是现实风险。

## 决策

- `deepseek-harness/` 固定 commit
  `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`。
- 产品运行闭包固定 npm `@deepseek-ai/dsh@0.1.1-rc.2`，版本必须与 pin
  对应；submodule 用于源码审计、上游构建和回归，不是产品运行路径。
- `patches/` 在 M1 保持为空，`upstream.json#patches` 是补丁清单真源。
- pin 更新与产品行为修改必须分开提交；先 dump 基线，再逐项执行真实启动、
  生命周期、鉴权与打包回归。

## 被否方案

- **跟随 master**：无法复现运行闭包，也无法判断回归来自上游还是产品。
- **只锁 npm、不保留 submodule**：失去 provider/API/ABI 的可审计源码和
  上游自身构建门禁。
- **继承参考桌面的补丁集**：那些补丁服务于另一套完整产品，M1 没有逐条
  证明其必要性。

## 可证伪的验收证据

- `.gitmodules` 使用 HTTPS，gitlink、checkout、`upstream.json` 三者一致。
- `git -C deepseek-harness status --porcelain` 为空。
- `yarn upstream:install && yarn upstream:build` 通过。
- before/after `dump-config` 证据可解释，补丁清单为空。

## 遗留风险

rc 版本可能改变 profile、Client module wrapper 或 WebServer 契约。升级时
必须重新阅读 release/breaking notes，并把不兼容处理写成新的 Agent Note。
